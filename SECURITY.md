# Current deployment: native Worker Access
The Worker is named `chatgpt`. Enable Worker-level Cloudflare Access using its Access tab. The server reads Cloudflare's trusted `ctx.access.getIdentity()` and requires the configured owner email. No copied team URL, AUD tag, or session secret is needed for this mode. Missing identity or a different email is denied.

Assets are bundled by `scripts/bundle-assets.mjs` and served by the authenticated Worker. Do not add a Wrangler static assets binding: Cloudflare's internal assets router does not propagate ctx.access. Run npm run build before deploying.

Turnstile is optional in native Access mode and is NOT active without its three settings (site key, secret key, session secret). Setting any one without the others keeps access closed. Existing fully configured JWT/Turnstile mode remains supported. The older manual configuration instructions below apply to that mode only.

# Security boundaries

- GitHub Pages publishes `public-closed/` only, with no dashboard or child assets. Legacy Jekyll publishing excludes source/build folders through `_config.yml`; never restore root `.nojekyll` while using branch publishing.
- The private app is built into `dist/` and served exclusively through the Cloudflare Worker. `assets.run_worker_first` must remain true. Production login must cover the entire hostname. Preview URLs are disabled.
- Authentication uses Cloudflare Access RS256 JWTs verified by `jose` against that team's JWKS. The exact owner email is required; email headers alone are never trusted.
- Turnstile is verified server-side. A signed verification cookie is bound to the identity and origin, expires after an hour, and does not replace Access authentication.
- Missing configuration, invalid identity, failed verification, and verification-service outages deny protected assets. Private responses are not cacheable.
- Only static child projects are served. External project URLs have their own access rules; linking to a third-party URL does not make that third-party app private.
- Source privacy requires a private repository. A public Git repository, old deployments, downloaded artifacts, and repository history are outside the Worker's protection. Never commit secrets.
- Dock `dock-*` localStorage keys sync through `/api/project-sync` to the owner-only Durable Object. The browser also retains a local copy for offline use. Cloudflare Access protects server data, but it is not end-to-end encrypted and must not be used as a secret store. Backups may include all saved project records and preferences.

Run `npm test` for authentication and bot-verification boundary checks. Read `cloudflare-setup.md` before enabling private hosting.

## Streamed browser
The /_browser gateway runs after the owner check and any configured Turnstile check. WebSocket upgrades require the hub's exact Origin and a fixed HTTPS upstream configured by the administrator. The upstream receives only its dedicated shared secret, not Access JWTs, browser cookies, or client Authorization headers. The Mac service rejects unauthenticated upgrades before launching Chromium. It uses temporary contexts, browser sandboxing, a public-IP-only CONNECT proxy, blocked permissions/downloads/popups, input limits and session expiry. Its Mac launcher and hosting requirements are documented in services/browser/README.md. Do not expose the browser service or Chrome DevTools without authentication. No remote server credentials belong in client-side files or Git.

## Tasks push reminders
The authenticated `/api/tasks-push` gateway requires the existing owner identity; mutation requests must be same-origin JSON. `TaskPush` uses a SQLite Durable Object and alarms. VAPID private keys are generated and kept in server storage, never browser JavaScript or Git. The notification scheduler stores device identifiers, browser push endpoints, reminder IDs/times, optional repeat rules/time zones and delivery bookkeeping. Separately, project sync stores full saved task records in the owner-only workspace Durable Object. Push destinations are restricted to known HTTPS browser push providers with redirects disabled. The service worker receives payload-free pushes and reads task names/due dates from a device-local IndexedDB mirror to display detailed reminders, with a generic fallback. Task content is not sent in push messages or to the push provider; the separate project-sync API stores it in the owner-only workspace for cross-device access. It has no fetch/offline asset cache handler. Persistent `dock-*` localStorage entries sync over same-origin JSON to `/api/project-sync`; session drafts and notification device IDs are excluded. The API requires the same Access identity, any configured Turnstile session, and same-origin mutation requests. Browser and OS notification permissions are required. Push acceptance does not prove display on the device. See `projects/tasks/NOTIFICATIONS.md` for setup, retention and delivery limits.

## Shared Video Call exception

The Video Call project deliberately admits any identity already authenticated by native Worker Cloudflare Access, on the call pages, call API and a fixed list of generic static assets only. Owner project pages, workspace sync, Tasks/GroupMe APIs and all other data stay owner-only. It does not add an anonymous access path. Guest access still requires an Allow entry in the external Cloudflare Access policy. Call pages disable owner data sync and store no persistent workspace data. Random room invites, two-session capacity, identity-bound peer IDs, same-origin JSON checks, bounded signals, cursored queues and short room expiry protect signaling. WebRTC media is not recorded; optional Cloudflare TURN API credentials stay server-side and generate short-lived client ICE credentials. See `projects/video-call/README.md`.

## Jane’s member workspace and owner preview

The user-authorized member workspace extends the shared-call exception: non-owner native Access identities receive a dedicated Jane welcome hub and a filtered two-project catalog (Video Call and GroupMe Messages). Other project assets/APIs remain owner-only. `/api/groupme/*`, GroupMe push and account connection are routed to a `MEMBER_ACCOUNTS` Durable Object named from the authenticated email, never a caller-supplied user ID. That object explicitly clears the global owner GroupMe token and loads only its own verified credential, including after restart and during notification alarms. Account connect responses never return tokens; browser storage does not store them. Tokens are server-side credentials, not end-to-end encrypted from the server operator. Jane connects her own GroupMe Developer access token from her GroupMe project page; no password is collected.

Member project synchronization has a separate `member:<identity>` namespace and accepts only appearance/GroupMe record keys. Browser local/session storage methods are namespaced per authenticated member; owner keys are preserved. The identity bootstrap loads before project sync/appearance on every project page. Same-origin fetches carry a workspace fingerprint checked against the server identity, preventing a stale tab or expired owner preview from falling back to the owner's account. This header only adds a consistency check and is never used as authentication or to select someone else's storage.

Owner preview is an authenticated downgrade selected by an owner-only, same-origin POST, backed by a Secure/HttpOnly/SameSite cookie. It uses a distinct `preview:<owner>` member account and browser namespace, not Jane's real account or the owner's GroupMe token. Preview cannot fetch owner-only assets/APIs. Disabling preview reloads the normal owner workspace; it does not delete owner data. Non-owners cannot enable/disable owner preview. Access login and optional Turnstile protections remain required.
